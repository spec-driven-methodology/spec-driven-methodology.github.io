Spec-Driven Methodology

SDM — методология обращения с методическими артефактами как со спецификациями: пишутся один раз, проверяются машинно, а всё производное генерируется. Спроектирована для эпохи ИИ: человек задаёт направление, AI-агент исполняет процесс.

agent-first — работу делает AI-агент, контроль остаётся у человека
Проблема

Методология живёт везде и нигде

До SDM методические артефакты разбросаны по Wiki, Excel, LMS — без единого источника правды и без честного ответа на вопрос «что покрыто?».

Разъехавшиеся матрицы

Матрицы компетенций в Wiki, Excel, LMS — везде своя версия. Никто не знает, какой файл актуальный.

Нет проверяемого покрытия

Нет воспроизводимого ответа «чем закрыт langchain4j для Java Middle». Покрытие живёт в голове эксперта.

Оценка ≠ обучение

Отдельные контуры: тесты для найма, курсы для онбординга — без общего графа навыков. Поправил навык — правь всё руками.

AI ускоряет хаос — и даёт решение

AI ускоряет производство контента, но без каркаса из спек получается быстрее больше хаоса. SDM даёт AI-агентам машиночитаемый скелет, внутри которого они работают: человек определяет онтологию и пороги, агенты считают покрытие и генерируют экспорт. Качество = спеки × агент × модель.

Отслеживаемая онтология

Навыки, темы, концепты в едином графе — больше никаких «в каком Excel актуальная версия».

Верифицируемое покрытие

Фиксированное определение gap: одинаковые онтология + профиль → одинаковые пробелы у любой реализации. Воспроизводимо, а не «на глаз».

Переиспользование без копий

Одна онтология питает много профилей. Один банк вопросов — разные срезы, без дублирования контента.

Независимость от инструмента

CLI, MCP, Obsidian, веб — реализации конкурируют, методология остаётся той же. Смена среды не ломает процесс.

Контроль изменений

Правишь спеку в одном месте — покрытие и экспорт пересобираются контролируемо. Без ручного поиска, что задел.

AI-native процесс

Человек формулирует намерение естественным языком — AI-агент уточняет, планирует и исполняет через MCP/CLI. Вы ревьювите.

Концепт

Что такое SDM?

Единая, машинно-проверяемая цепочка методических артефактов — неважно, кто выполняет шаги: человек или агент.

ONTOLOGY

Единый граф

Узлы любых видов — навыки, темы, концепты, доклады — и их связи в одном графе.

PROFILE

Выборка и порог

Что отбираем из онтологии и до какого порога. Профиль определяет цель.

COVERAGE

Фиксированное определение gap

Чего не хватает — множество gap-узлов по фиксированному определению, одинаковому для всех реализаций.

Как устроено

Жизненный цикл

Артефакты, а не команды — цепочка одна, кто бы её ни исполнял.

Онтология

Граф узлов и связей, любые виды.

Профиль

Выборка из онтологии с порогом.

Покрытие

Gap-узлы по фиксированному определению.

Экспорт

Результат уходит в MCP, Obsidian, веб, CLI, документы.

AI-native

Agent-first: человек говорит намерением — агент исполняет

SDM спроектирована для эпохи ИИ с самого начала. Человек описывает, что нужно — AI-агенты делают тяжёлую работу в границах спек.

Человек говорит намерением

«Нужна основа профиля Java Middle с AI/LLM». Агент уточняет, показывает план, ждёт подтверждения. Никаких флагов CLI. Никакого YAML руками.

Агент исполняет

Агент вызывает SDM через CLI/MCP: создаёт навыки, добавляет вопросы, считает покрытие, экспортирует артефакты. Остаётся в рамке — не может нарушить инварианты.

Вы ревьювите результат

Отчёт о покрытии, превью экспорта — вы говорите «ок» или «поправь вот это». Агент итерирует. Контроль у вас, работу делает агент.

Цикл продолжается

Агент предлагает следующие шаги: закрыть пробелы, усилить качество, экспортировать под новую поверхность. Та же рамка, по состоянию методологии.

Намерение · Spec-Driven Methodology · Агент

Человек → Агент + LLM → CLI / MCP / skills → SDM → Спеки YAML

Качество = спеки × агент × модель. Методология ограничивает агента — она не выбирает определение gap и не обходит валидацию.

Границы

Чем не является

Чёткие границы помогают сохранять фокус.

Не SDD (это про код)
Не инструмент/продукт — CLI, MCP, плагины — это реализации
Не формат хранения (YAML не обязателен)
Не LMS и не платформа тестирования
Не judge/судья — проверки качества контента вне методологии
Не про вопросы только — элементы профиля могут быть любыми
Аудитория

Кому

Методисты, преподаватели, учителя, блогеры, организаторы конференций — любой, кто работает с методическими артефактами и хочет проверять их на полноту.
